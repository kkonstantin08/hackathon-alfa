# Контракт взаимодействия четырёх AI-агентов

> Версия 0.1 от 24.10.2026. Согласованные правила четырёх участников; технические ограничения отмечены отдельно.

Этот документ задаёт взаимодействие участников разработки. Контракты данных приложения описываются отдельно в `docs/CONTRACTS.md` и `contracts/models.py`.

## 1. Участники и ответственность

| ID | Человек | Основная область | Рекомендуемый независимый ревьюер |
| --- | --- | --- | --- |
| A | Александр | `app/profiles/`, `app/ranking/`, правила экспозиций, измерение качества | B — Константин |
| B | Константин | `app/news/`, `app/bank_kb/`, источники, обработка PDF, поиск | D — Тимофей |
| C | Алексей | `contracts/`, `app/llm/`, `app/agent/`, `app/api/`, серверные ошибки и интеграция | A — Александр |
| D | Тимофей | `web/`, Docker, CI, инструкция и пользовательская демонстрация | C — Алексей |

Это маршрутизация ответственности, а не разрешение параллельно менять чужие файлы. Исключительное исполнение frontend закреплено за Тимофеем. Изменения на границах областей сначала обсуждаются с их владельцами.

Общую очередь и обзор STATUS ведёт Константин. Контрактные изменения координирует Алексей, получая подтверждение потребителей. Это обязанности существующих участников; пятый координатор или дополнительный агент не создаётся.

Вторым исполнителем может быть только Алексей. В Issue записывается конкретная область его помощи. Основной исполнитель отвечает за целый результат. Участие в реализации исключает человека и его агента из независимого ревью этого PR, даже если он указан обычным ревьюером.

Для задачи упаковки D-05, где помогает Алексей, рекомендуется Константин. Любой другой из четырёх участников, не участвовавший в реализации PR, может выполнить независимое ревью и дать GitHub Approval. Указанное имя задаёт первого адресата, а не исключительное право одобрения: ждать его или получать разрешение на замену не требуется. Фактический ревьюер указывает себя в отчёте до одобрения. Автор и все соисполнители этого PR исключены из независимого ревью и одобрения.

GitHub-логины пока не сопоставлены именам. Не выдумывать аккаунты. Имена в Issue — организационное назначение; реальные Assignees, review requests, CODEOWNERS и адресные уведомления включаются только после проверки аккаунтов и прав.

## 2. Канал взаимодействия

Общий канал — Issues и PR репозитория `kkonstantin08/hackathon-alfa`. Связанные документы хранят решения, а не вторую копию статусов.

- Назначение, готовность входов и блокеры — в Issue задачи.
- Изменение общего интерфейса — в Issue и связанном PR со ссылками на потребителей.
- Запрос ревью, замечания и решение — в PR.
- Готовность результата к использованию — HANDOFF в Issue со ссылкой на принятый PR или точный доступный коммит.

Личный чат, терминал и рабочая память модели не являются общим каналом. Не считать сообщение прочитанным без подтверждения получателя, когда требуется его решение.

GitHub не запускает локальные агенты автоматически. Контракт работает, когда участники запускают свои сессии и читают обсуждения в описанные моменты. Непрерывное ожидание сообщений, автоматические пробуждения и общий сервер Agent Mail этим документом не устанавливаются.

## 3. Карточка задачи

Каждый Issue содержит:

1. Один проверяемый результат и границы работы.
2. Основного исполнителя и его роль; Алексея как второго исполнителя только при необходимости.
3. Рекомендуемого независимого ревьюера; проверить и одобрить PR может любой другой участник, не являющийся соавтором.
4. Входы, производимые интерфейсы, потребителей и зависимости.
5. Пять конкретных acceptance criteria с пустыми чекбоксами до проверки.
6. Способ проверки и необходимые внешние доступы.
7. Один актуальный статус и ссылки на PR и отчёты.

Обычная задача — ориентировочно 1–3 часа активной работы. Большую задачу разделяют по самостоятельным результатам. Код, необходимые тесты и документация одного результата остаются вместе.

IDs A-01, B-01 и подобные — обозначения согласуемого плана. До публикации они не являются номерами GitHub. При создании Issues зависимости заменяются реальными ссылками.

## 4. Статусы и переходы

| Статус | Условие перехода | Кто фиксирует |
| --- | --- | --- |
| Backlog | Задача описана, но входы, доступ или очередь ещё не готовы | Основной исполнитель или координатор |
| Ready | Есть согласованные входы/примеры, понятен следующий шаг и доступен результат зависимостей либо их стабильный контракт | Основной исполнитель |
| In progress | Владелец подтвердил взятие задачи сообщением START и проверил пересечения | Основной исполнитель |
| Blocked | Названа конкретная причина, адресат и требуемое действие | Основной исполнитель |
| In review | PR готов, проверки опубликованы, отправлен READY_FOR_REVIEW | Основной исполнитель |
| Ready to merge | Актуальный CI зелёный, независимое ревью завершено, замечания разрешены по правилам | Основной исполнитель со ссылками на доказательства |
| Done | Результат принят и PR включён по человеческой команде | Основной исполнитель после проверки результата |

Blocked возможен из активных состояний. После устранения причины возвращаются в подходящее состояние, сохраняя историю. После изменений по ревью задача возвращается в In progress, затем проходит необходимые проверки и In review.

Незавершённая зависимость сама по себе не переводит задачу в Blocked. Ожидание очереди или входов обозначается Backlog. Если согласованный контракт и примеры позволяют начать независимую работу, используется Ready. Blocked требует конкретного препятствия, его влияния, адресата и действия для устранения; не назначается автоматически всем зависимым задачам.

Для административной задачи Done означает реально применённую и проверенную настройку. Для координационного Issue — завершённую репетицию и фиксацию ограничений. Написанная инструкция и открытый PR сами по себе не закрывают эти задачи.

У каждого человека одна основная задача In progress. Короткое чужое ревью может прервать её. Помощь Алексея согласуется с его текущей загрузкой и не начинается одновременно во всех задачах.

## 5. Формат сообщений

Обязательные поля сообщения:

```text
Тип: START | CONTRACT_CHANGE | BLOCKED | READY_FOR_REVIEW | HANDOFF
Задача: ссылка на Issue
Отправитель: имя и роль
Получатель: имя и роль либо конкретные потребители
Результат или проблема: краткий проверяемый факт
Артефакт: ссылка на PR, документ или отчёт; base/head SHA для кода
Требуемое действие: что именно должен сделать получатель
```

Для контрактного предложения также указываются старое и новое поведение, совместимость и порядок перехода. Для блокера — отсутствующий вход/доступ, влияние на задачу и следующая точка проверки. Для передачи результата — способ запуска, проверенные случаи и ограничения.

### START

Перед существенными изменениями исполнитель проверяет назначение и активные PR, сообщает область правок и переводит задачу в In progress. Сам комментарий не является атомарной блокировкой файлов. Конкурирующее назначение сначала разрешается между владельцами.

### CONTRACT_CHANGE

Отправляется до несовместимого изменения. Потребители отвечают в том же обсуждении: принято; требуется переход; есть конкретное возражение. Молчание не считается согласием. Пока решение не получено, исполнитель сохраняет прежнюю совместимость либо продолжает независимую часть работы.

При принятии обновляются код контракта, реестр, примеры, проверки потребителей и план миграции в связанном PR. Изменение внутренней функции без внешних потребителей такого согласования не требует.

### BLOCKED

После примерно 30 минут безрезультатного разбора внешнего препятствия исполнитель фиксирует блокер и выбирает доступную независимую работу. Это ориентир остановки бесполезного ожидания, а не автоматический таймер. Критическую несовместимость или риск для общего результата сообщают сразу.

### READY_FOR_REVIEW

Отправляется только после проверки собственных критериев и необходимых тестов. Содержит точные base/head SHA, описание результата, выполненные команды, ограничения и имя независимого ревьюера. Просьба посмотреть ещё не готовый PR помечается как консультация, а не итоговое ревью.

### HANDOFF

Указывает, какой результат доступен, в какой версии, как его получить и проверить. Для ещё не принятого PR явно пишется, что результат существует только в ветке и не находится в main. Потребитель подтверждает получение и обнаруженную совместимость либо публикует BLOCKED.

Повторные одинаковые сообщения объединяются в одном обсуждении. Новая версия кода получает новый head SHA. Изменение состояния подтверждается ответом или доказательством; молчание, вывод в терминале и прочитанный локальный файл подтверждением не являются.

## 6. Когда читать сообщения

Каждый агент читает свой Issue, зависимости и связанные PR:

- в начале сессии;
- перед изменением общего интерфейса;
- перед началом новой большой задачи;
- перед открытием или обновлением готового PR;
- при переключении на ревью и после получения замечаний;
- перед передачей результата и закрытием задачи.

На утреннем и вечернем коротком синке люди проверяют блокеры, контракты, очередь ревью и ближайший сквозной результат. Константин обновляет обзор. Эти синки не заменяют немедленное сообщение о несовместимости.

## 7. Независимое ревью

Тот же личный AI-агент фактического ревьюера работает в новой сессии. Проверку может взять любой из четырёх участников, не участвовавший в реализации PR; рекомендуемое назначение не ограничивает этот выбор. Агент получает требования задачи, полный diff, base/head SHA, необходимые соседние исходники и контракты. Сообщения исполнителя — исходные сведения, а не доказательство корректности.

Ревью выполняется без редактирования, коммитов, push и merge. Используется отдельная рабочая копия и технический доступ только на чтение, когда это доступно. Если ограничения не обеспечены инструментом, это явно указывается, а текстовая инструкция не называется sandbox-изоляцией.

Обязательная проверка — корректность поведения и применимые требования проекта. Дополнительные направления выбираются по риску: данные, авторизация, совместимость, ошибки, ресурсы или UI. Дополнительные постоянные агенты не создаются.

### Отчёт

Отчёт публикуется в соответствующем PR и содержит:

- имя и роль ревьюера, известные среду/модель; неизвестную модель не выдумывать;
- точные base/head SHA;
- какие изменения и связанные интерфейсы проверены;
- результат PASS, CHANGES_REQUIRED или INCOMPLETE;
- замечания с приоритетом, файлом/строкой, сценарием, последствиями, основанием и направлением исправления;
- выполненные проверки и существенные ограничения.

P0 — критический блокер; P1 — серьёзная ошибка, блокирующая слияние; P2 — подтверждённый дефект, требующий исправления или явного решения человека. Косметические предпочтения и несвязанный редизайн не блокируют PR.

Ревьюер проверяет контекст и объединяет дубли. Балл уверенности и совпадение мнений моделей не заменяют доказательства. Отсутствие находок допустимо.

PASS означает завершённую проверку выбранного diff без неразрешённых блокирующих замечаний. Он не подтверждает весь репозиторий и не разрешает deployment. Оставшийся P2 требует отдельного человеческого решения, отражённого рядом с результатом.

Неполный diff, отсутствующий существенный контекст, тайм-аут и незавершённая оценка означают INCOMPLETE. Отсутствие отчёта не означает PASS.

### Исправления и актуальность

Исполнитель проверяет замечания, исправляет подтверждённое, отклонённое объясняет. При изменении кода обновляются head SHA и необходимые проверки. Ревьюер проверяет новую дельту и её влияние на ранее просмотренный код; старый PASS не переносится автоматически.

После двух содержательных циклов оставшийся спор передаётся людям с доказательствами. Нельзя ослаблять критерии, тесты или приоритет дефекта ради формального успеха. Ревью приоритетно перед началом следующей большой реализации, чтобы четыре человека не ожидали друг друга без движения.

Успех на синтетических fixtures не выдаётся за качество на реальных данных. Отсутствие ключа, материала или доступа оставляет соответствующий критерий открытым. Финальная проверка обнаруживает несовместимости и фиксирует ограничения; обещания отсутствия любых интеграционных ошибок не даются.

## 9. GitHub, приёмка и полномочия

Одна задача обычно соответствует одному небольшому PR. Ветка и рабочая копия изолированы от чужой работы. Автор указывает связанный Issue, критерии, контракты, проверки, ревьюера и ограничения.

Нормальное слияние требует зелёного обязательного CI на актуальном коммите, завершённого независимого AI-ревью, решения по замечаниям и одного одобрения любого другого участника команды, не участвовавшего в реализации PR. GitHub одобряет человек из своего аккаунта после проверки отчёта; AI-текст не является самим GitHub Approval. Одобрение конкретного рекомендованного ревьюера или всех участников не требуется.

Merge и deployment требуют отдельных явных человеческих команд. Не пользоваться административным bypass как обычным способом слияния. Действующие аварийные правила не обходят обязательный CI и не отменяют требование человеческого решения.

Настройка защиты main и сброса устаревших одобрений принадлежит владельцу с admin-доступом и проверяется в ADMIN-01. Обязательными назначаются реально существующие CI jobs. Пока правила не применены, документ не считается технически установленной защитой.

Этот контракт не устанавливает плагины, подписки, разрешения на чужих машинах, API-ключи, платный хостинг или автоматического бота. Технические ограничения и недоступные функции указываются в отчётах.
