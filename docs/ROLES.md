# Работа команды на первых шагах

> План старта с учётом уточнения пользователя от 20.10.2026, [Issue #1](https://github.com/kkonstantin08/hackathon-alfa/issues/1). Сначала все готовят данные для общего минимально работающего анализатора. Анкетные специальности пока не определяют задачи; буквы A–E нужно заменить именами участников.

## Что значит независимость задач

Все пять задач можно начать и завершить параллельно. У каждой свои входы, примеры, запуск и проверка. Входы берутся непосредственно из исходных материалов кейса или внешнего источника, а не из результатов другого участника. Общая база, сервис другого участника, общая выборка компаний и предварительное согласование полного API не нужны.

Для старта всем нужен доступ к исходным материалам. Участнику E дополнительно нужен доступ к разрешённой LLM; ключ и параметры доступа не являются результатом задач A–D. Если доступа нет, это внешний блокер живой проверки E, его нельзя скрывать подменой модели или моками. A–D не требуют общего генеративного API.

## Пять независимых задач

| Участник | Входы, доступные сразу | Задача и самостоятельный результат | Проверка без результатов коллег |
| --- | --- | --- | --- |
| A — компании | Оригинальный `df_Uid_data_hack.csv` | Проверить типы, единицы, пропуски и различия признаков; подготовить словарь полей, загрузчик и несколько контрастных профилей | Выбрать компании самостоятельно из CSV. Повторно получить профили, проверить исходные значения и пропуски на собственных небольших примерах |
| B — платежи и связи | Оригинальные CSV платежей и физических лиц; CSV компаний для проверки ID при необходимости | Проверить связность, дубли и направления платежей; подготовить загрузчик и простые агрегаты связей по исходным ID | Самостоятельно выбрать ID из исходников, сверить суммы/число платежей и нераспознанные связи. Профили и выбранные компании A не используются |
| C — аналитика банка | Девять оригинальных PDF | Извлечь текст, даты и страницы; подготовить фрагменты с происхождением и простой поиск | Самостоятельно составить поисковые вопросы по содержанию PDF. Проверить найденные фрагменты в оригинале; новости D и примеры E не нужны |
| D — новости | Выбранные доступные внешние источники | Подготовить небольшой разнообразный корпус, сборщик/загрузчик, URL, время, дедупликацию и отдельную часть для будущей проверки | Проверить загрузку, метаданные и повторы на собственных сохранённых примерах. Профили A и поиск C не используются |
| E — пробный анализатор и проверочные примеры | Небольшие примеры, самостоятельно выбранные прямо из исходных CSV/PDF и новостных первоисточников; разрешённая LLM | Вручную собрать несколько входов «профиль + новость + фрагмент банка», основания ожидаемого влияния и воспроизводимый запуск модели с проверкой ответа | Работать только со своим фиксированным набором, без импортов, сервисов и данных A–D. Проверить контрастные компании, нехватку данных, происхождение выводов и расход |

Ручная подготовка E касается только нескольких контрольных примеров. Массовую обработку E не дублирует: загрузчики A–D будут подключены позже. Однократная генерация здесь — базовая проверка осуществимости, а не выполненное требование кейса к агентной логике.

Каждый передаёт собственные подготовленные данные, небольшой скрипт/ноутбук, инструкцию запуска, воспроизводимую проверку и ограничения. Сырые банковские данные не коммитятся в публичный репозиторий; публичные примеры должны быть синтетическими. Полные исходники каждый читает локально.

## Как избежать скрытых зависимостей

- Каждый работает в отдельной ветке и своей области файлов. Нет обязательного общего сервиса, общего окружения или общего файла, который должны одновременно менять все.
- Внутри своей задачи каждый вправе выбрать формат хранения и библиотеки. В исходных ID сохраняется точное значение; для полученных признаков и фрагментов сохраняется происхождение. Общие ориентиры перечислены в [CONTRACTS.md](CONTRACTS.md), но они не требуют результата или согласования другого исполнителя для старта.
- У каждого свои небольшие примеры для проверки. B не ждёт списка компаний A; C не ждёт корпуса D; E не ждёт ни одного загрузчика или поиска коллег.
- Готовность задачи определяется её собственным запуском и проверкой. Изменения соседних задач и объединение всех веток не входят в её критерии завершения. Обычные правила PR и человеческого ревью сохраняются.
- Если обнаружена проблема исходных данных, участник фиксирует её и показывает проверяемый частичный результат. Он не перекладывает завершение своей задачи на подготовку данных коллегой.

## Отдельный этап: совместная сборка

После самостоятельной сдачи A–E команда создаёт отдельную интеграционную задачу. В ней выбираются общие примеры, согласуются окончательные форматы или небольшие адаптеры, загрузчики A–D подключаются к пробному анализатору E. Различия форматов и выборок решаются здесь и не блокируют сдачу исходных задач.

Общий результат: профиль компании + новость + подходящие фрагменты банка → разбор с проверяемыми основаниями; полезные связи B включаются по результатам проверки данных. При недостатке оснований анализатор выдаёт явное ограничение. Затем проверяются другая компания и новая новость, не использованная для настройки. Достаточно скрипта/ноутбука.

## Когда переходим к профильным ролям

После совместного запуска и оценки слабых мест команда распределяет разработку по навыкам и анкетным профилям: агент/RAG, backend, frontend/UI/UX, интеграция и развёртывание. Постоянные владельцы, полный API и UI не требуются для пяти стартовых задач; требования финальной сдачи сохраняются.

## Правила

- Перед выполнением своей задачи каждый человек с агентом заполняет личный `ROLE.local.md` по `ROLE.example.md`: можно указать временную ответственность за выбранные данные без закрепления постоянной специальности. Файл не коммитится.
- Указать реальные имена/GitHub handles и другого человека для ревью. Автор не является собственным обязательным ревьюером.
- Исполнитель выбирает внутренние детали. Общие схемы, API, окружение и объём MVP обсуждаются по [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md).
- Можно менять соседний модуль в рамках Issue; до изменения общей границы уведомить конкретных потребителей в Issue/PR.
- Агенты могут создавать ветки, коммиты, push и PR. Merge — только по отдельной явной команде человека, с соблюдением ревью и CI.
- Для Codex сохраняется политика проекта: основной агент `gpt-6.1-sol` / `medium`, исполнители `gpt-6-luna` / `high`, максимум два активных субагента, включая вложенных. Это настройка разработчиков, а не выбор LLM продукта.

Ближайшее действие — распределить A–E по людям, проверить доступ к исходникам и модельному API, уточнить время и создать пять независимых Issues. После их сдачи завести отдельную интеграционную задачу. Координатора контрольной точки выбрать временно, без закрепления профильной роли.
