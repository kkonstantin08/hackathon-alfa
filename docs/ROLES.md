# Работа команды на первых шагах

> План старта с учётом уточнения пользователя от 20.10.2026, [Issue #1](https://github.com/kkonstantin08/hackathon-alfa/issues/1). Сначала все готовят данные для общего минимально работающего анализатора. Анкетные специальности пока не определяют задачи; буквы A–E нужно заменить именами участников.

## Общий результат первого этапа

Профиль компании + новость + подходящие фрагменты аналитики банка → разбор с объяснением влияния и проверяемыми основаниями. На этом этапе достаточно общего запуска скриптом или ноутбуком. Под работающей моделью здесь понимается анализатор на разрешённой LLM; обучение собственной модели не является условием старта.

## Пять стартовых задач

| Участник | Что делает с данными | Что передаёт в общий анализатор | Как проверить вклад |
| --- | --- | --- | --- |
| A | Исследует `df_Uid_data_hack.csv`: типы, пропуски, единицы, различия признаков; готовит профили | Словарь проверенных полей, загрузчик и несколько контрастных профилей с исходными значениями и ID | Профили повторно получаются из CSV; неизвестное не превращается в факт |
| B | Исследует платежи и связи физических лиц: совпадение ID, дубли, пропуски и полезность связей | Загрузчик и простые агрегаты связей для тех же компаний: плательщики/получатели, суммы/число платежей, доступные связи; ограничения интерпретации | Проверены направления платежей и связь с профилями A; нераспознанные ID и отсутствие данных явно отмечены |
| C | Разбирает девять PDF банка: извлечение текста, даты, страницы, фрагменты и поиск | Набор фрагментов с происхождением и простой способ найти подходящие к событию; примеры удачного и неудачного поиска | Каждый фрагмент можно найти в оригинале; старая аналитика не выдаётся за текущую позицию |
| D | Выбирает доступные источники новостей и собирает небольшой разнообразный корпус | Простой сборщик/загрузчик, тексты с URL и временем, удаление повторов; отдельная часть новостей для итоговой проверки | Есть разные события, сохранены первоисточники; проверочные новости не используются для настройки |
| E | Готовит проверочные пары «компания × новость» и основания ожидаемого влияния; сначала на небольших примерах, затем на данных A–D | Таблица примеров с признаками и ссылками, общий вход/выход для пробного запуска разрешённой LLM и проверки её ответа | Есть контрастные компании, случаи нехватки данных и неподходящей аналитики; критерии проверяют основания, а не совпадение с заранее написанным текстом |

Каждый сдаёт пригодный к повторному использованию набор данных и небольшой способ его получить или проверить, а также кратко описывает ограничения. Только чтения материалов и устного отчёта недостаточно. Сырые банковские данные не коммитятся в публичный репозиторий; общие примеры в GitHub — синтетические.

Задачи можно начинать параллельно: идентификаторы и имена полей берутся из кейса, E сначала готовит формат примеров и критерии. После первых результатов A команда выбирает общие компании; B и E уточняют свои наборы. Объём каждой задачи пересматривается, если обнаруживаются сканы PDF, плохой текст новостей или проблемы связности данных.

## Как собираем первый результат

1. Вместе согласовать минимальные форматы профиля, связей, новости, фрагмента банка и проверочной пары. Имена участников и конкретные Issues пока не назначены.
2. Каждый готовит свой первый небольшой пригодный пример, не дожидаясь полного исследования всех файлов.
3. Совместно соединить результаты A–E в один запуск: выбрать компанию и событие, найти основания, вызвать разрешённую модель, проверить вывод. Техническую сборку распределить между участниками, а не закреплять заранее за «backend» или «ML».
4. Повторить запуск для другой компании и новой новости; отдельно проверить отсутствие нужных данных. Каждый проверяет хотя бы один результат другого участника.

## Когда переходим к профильным ролям

Контрольная точка — общий анализатор запускается повторно, использует подготовленные данные всех пяти участников и выдаёт проверяемый разбор либо обоснованный частичный ответ. По этой проверке понятны слабые места и оставшиеся задачи.

После этого команда распределяет разработку по навыкам и анкетным профилям: агент/RAG, backend, frontend/UI/UX, интеграция и развёртывание. Точные границы выбираются по фактической работе. Полный UI, API и деплой не являются условием завершения первого этапа; требования финальной сдачи сохраняются.

## Правила

- Перед выполнением своей задачи каждый человек с агентом заполняет личный `ROLE.local.md` по `ROLE.example.md`: можно указать временную ответственность за выбранные данные без закрепления постоянной специальности. Файл не коммитится.
- Указать реальные имена/GitHub handles и другого человека для ревью. Автор не является собственным обязательным ревьюером.
- Исполнитель выбирает внутренние детали. Общие схемы, API, окружение и объём MVP обсуждаются по [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md).
- Можно менять соседний модуль в рамках Issue; до изменения общей границы уведомить конкретных потребителей в Issue/PR.
- Агенты могут создавать ветки, коммиты, push и PR. Merge — только по отдельной явной команде человека, с соблюдением ревью и CI.
- Для Codex сохраняется политика проекта: основной агент `gpt-6.1-sol` / `medium`, исполнители `gpt-6-luna` / `high`, максимум два активных субагента, включая вложенных. Это настройка разработчиков, а не выбор LLM продукта.

На первом обсуждении нужно распределить A–E по людям, уточнить доступное время и дедлайн, согласовать обмен данными и завести Issues. Решения по web-стеку и полному API можно отложить до первого общего запуска. На контрольную точку выбрать координатора, чтобы STATUS.md не редактировали одновременно все пятеро.
