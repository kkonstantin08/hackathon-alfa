# Новостная аналитика для руководителей бизнеса

Прототип для хакатона «Альфа Будущее» (кейс «Новостная аналитика для принятия бизнес-решений»).
Сервис показывает руководителю компании ленту новостей, отсортированную под профиль его бизнеса, и для каждой
новости строит карточку: что произошло, почему важно именно ему, риски и возможности, что сделать, позиция банка
и на чём основан вывод. Каждое утверждение помечено «факт / банк / AI» и ссылается на источник.

## Архитектура

Модульный монолит на Python (FastAPI + SQLite) и статический фронт.

```
ЗАРАНЕЕ (python -m app.ingest)                ПО ЗАПРОСУ (FastAPI)
CSV клиентов ─► profiles (правила, без LLM) ┐   web ─► api ─┬─► ranking (формула, без LLM)
корпус новостей ─► news (Gemma: факторы, дедуп) ├─► SQLite ─┘   └─► agent: план → инструменты →
9 PDF банка ─► bank_kb (чанки, факторы, BM25) ┘                    черновик → проверка → ретрай
                                                               все вызовы моделей ─► llm-шлюз
```

- **Персонализация** — общий словарь факторов (`contracts/factors.yaml`). Профиль получает экспозиции по правилам
  (`contracts/exposure_rules.yaml`), новость — факторы от Gemma. Лента = формула совпадения с весом редкости фактора (idf).
- **Агент карточки** (`app/agent/flow.py`) — свой цикл без фреймворков: план из фиксированного набора инструментов,
  сбор доказательств, черновик со ссылками на источники, проверка кодом (источники, типы меток, числа) и судьёй (Gemma),
  повтор с ошибками, удаление неподтверждённого.
- **LLM-шлюз** (`app/llm/gateway.py`) — единственная точка вызова моделей: JSON-схема, кэш, бюджет, ретраи, трасса.

Подробнее: [docs/RULES.md](docs/RULES.md), документ архитектуры у команды.

## Запуск

```bash
cp .env.example .env          # по умолчанию LLM_MODE=mock — работает без сети
docker compose up --build     # http://localhost:8000
```

Без Docker:

```bash
uv sync
make ingest                   # профили, разметка новостей, индекс материалов банка
make run                      # http://localhost:8000, OpenAPI: /docs
make test                     # 16 тестов приложения + 4 проверки организационного каркаса
make eval                     # precision@5 / recall@5 ленты + доля карточек, прошедших проверку
```

Режим с моделями организаторов: в `.env` задать `LLM_MODE=live`, `LLM_BASE_URL`, `LLM_API_KEY`, имена моделей и цены.

## Переменные окружения

Полный список с комментариями — `.env.example`. Главные: `LLM_MODE`, `LLM_BASE_URL`, `LLM_API_KEY`,
`PLAN_MODEL` / `DRAFT_MODEL` / `CHAT_MODEL`, `DAILY_BUDGET_RUB`, `LLM_PRICES_RUB_PER_1K`, `DB_PATH`.

## Сценарий проверки

1. Открыть http://localhost:8000. Выбрана компания U001 (оптовая торговля зерном, ВЭД с Китаем, кредит и лизинг).
2. В ленте сверху — новости про зерно и юань с причинами «почему вам».
3. Переключить компанию на U002 (IT) — лента меняется: зарплаты IT, налоговые льготы.
4. Открыть новость — карточка из 6 блоков с метками и источниками. «Как получен вывод» — трасса шагов агента.
5. Задать вопрос в чате по новости.

## Данные

Все данные в `fixtures/` **синтетические**: 6 компаний в формате `df_Uid_data_hack.csv`, платежи, 20 новостей,
10 чанков-заглушек вместо материалов банка (помечены `[ЗАГЛУШКА]`). Реальные данные кейса подключаются через
`python -m app.ingest --companies ... --news ... --bank ...`.

## Известные ограничения

- В CSV продукты заданы флагами без сумм — последствия в рублях не считаются, только качественно.
- Лексический дедуп новостей слабый; при разрешённой модели эмбеддингов заменить на косинус (`EMBEDDINGS=on`).
- Формат API организаторов предполагается OpenAI-совместимым — проверить.
