# Хакатон: общий репозиторий для команды и AI-агентов

Готовый **шаблон организации работы**, а не исходный код будущего приложения. Рассчитан на 4 человека, 4–7 дней, один публичный GitHub-репозиторий (monorepo), Codex Desktop и Claude Code Desktop.

**До объявления кейса:** не заполняйте стек и продуктовые требования выдуманными решениями. Их согласуем на стартовой встрече.

## Старт за 20–30 минут

1. Создайте публичный репозиторий GitHub Free и перенесите в его корень **содержимое этой папки**, включая `.github/`, `.gitignore` и `AGENTS.md`.
2. Назначьте четырём участникам доступ **Write** (либо подходящую роль в организации). Откройте [GITHUB_SETUP.md](GITHUB_SETUP.md) и настройте правила `main`, Issues, Actions и merge — эти настройки **не применяются автоматически** при распаковке ZIP.
3. Каждый участник локально копирует `ROLE.example.md` в `ROLE.local.md`, вписывает свой GitHub-логин и временную ответственность за одну из четырёх стартовых задач. Постоянные функции определяются после общего прототипа. Этот файл **не отправляется в GitHub**.
4. Каждый ставит три набора навыков в используемую агентную систему по [docs/AGENT_SETUP.md](docs/AGENT_SETUP.md), проверяет Ponytail hooks и, если пользуется Codex, применяет пример `config/codex.config.toml.example` к личным настройкам.
5. Откройте проект в Codex Desktop или Claude Code Desktop и попросите агента прочитать `AGENTS.md`, `ROLE.local.md` и сообщить о недостающих настройках. Людям необязательно пользоваться CLI: установку командных компонентов можно поручить агенту, но права, хуки и изменения конфигурации необходимо лично подтвердить.

## В день открытия кейса

1. Обсудите [требования](docs/REQUIREMENTS.md) и четыре стартовые задачи. [Архитектура приложения](docs/ARCHITECTURE.md) остаётся предложением; стек, API и хостинг уточните после общего прототипа.
2. Распределите четыре независимые задачи из [ROLES.md](docs/ROLES.md) без привязки к анкетным специальностям. После общего прототипа четыре человека могут совмещать шесть функций.
3. Каждый выполняет свою задачу на исходных материалах и собственных примерах. Общие форматы для сборки и [контракты приложения](docs/CONTRACTS.md) согласуйте на отдельном этапе интеграции; они не блокируют независимую сдачу стартовых задач.
4. Создайте GitHub Issues, укажите исполнителя и критерии готовности. После обсуждения каждый исполнитель может записать свой короткий план в Issue. Обновляйте [STATUS.md](docs/STATUS.md) на контрольных точках.
5. DevOps/Integration подключает настоящие проверки сборки и тестов приложения и активирует CD по [GITHUB_SETUP.md](GITHUB_SETUP.md). **Автодеплой до выбора платформы ещё не действует.**

## Обычный цикл задачи

`Issue → агент создаёт ветку → изменения и тесты → Conventional Commits → push → PR → CI → ревью → явная команда человека на merge → автодеплой main`

- Агенту можно поручить создание ветки, коммиты, push и PR. **Merge только по явной команде человека.**
- Нормальный путь: хотя бы одно одобрение ревьюера + зелёный CI. Emergency Merge доступен любому участнику при человеческой команде, с указанием причины в PR, но без обхода CI.
- Чужую функциональную зону менять допускается; при обычном PR нужен ответственный ревьюер. Список зон и процесс — в [AGENT_WORKFLOW.md](docs/AGENT_WORKFLOW.md).
- GitHub Issues — источник правды по задачам; `STATUS.md` — короткий снимок общей картины, а не второй таск-трекер.

## Что уже работает, а что потребует настройки

- **Работает после push в GitHub:** GitHub Actions `CI / foundation` проверяет структуру шаблона и формат заголовка PR; тестируется стандартным Python без дополнительных зависимостей.
- **После выбора кейса:** добавьте в CI линтеры, тесты, typecheck и сборку приложения, сделайте их обязательными проверками.
- **После выбора хостинга:** настройте секреты и перенесите пример деплоя из `templates/` в `.github/workflows/`, заменив placeholder реальной командой развёртывания. Затем каждый merge в `main` будет запускать CD.
- **После настройки GitHub:** применяются защищённая ветка, правила ревью и особый путь Emergency Merge.
